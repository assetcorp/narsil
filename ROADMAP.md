# Roadmap

Narsil is a search engine that stores its indexes in the `.nrsl` binary format. A program in any language can load and save that format, because [`packages/spec`](packages/spec) specifies its layout. Any implementation that loads and saves the format counts as a valid Narsil. The TypeScript package is the reference implementation, so the maintainers check every other implementation against it.

The maintainers update this roadmap of planned work as the work proceeds. The roadmap contains no dates, since the plans in it can change. Open an issue to propose or discuss an item.

## Available now

Pattern search, partial-word search, synonyms, reranking, BM25 parameters, and changing an index's analysis are in the `next` tag on npm, and the next stable release will include them.

- **Embedded engine.** The engine answers full-text, vector, hybrid, and geographic searches inside your application process, in Node.js, Bun, Deno, or the browser.
- **Single-node server.** The HTTP server offers the same engine through a REST API, with a write-ahead log, bulk NDJSON import, and snapshots that you can restore.
- **The `.nrsl` format.** The engine saves every index in one binary format, so any runtime can load a file that another runtime writes.
- **Cluster mode.** The engine can operate across several nodes under `@delali/narsil/distribution`, where the cluster keeps every write that it acknowledges.
- **Pattern search.** A filter can find text inside the value of a pattern field, or test that value against a wildcard pattern or a regular expression.
- **Partial-word search.** A query word can also match inside longer words, so a search for `proof` can find `waterproof`.
- **Synonyms.** With a synonym set, a search for 'coat' can also return the documents that contain 'jacket'.
- **Reranking.** A query can reorder its top hits with a cross-encoder, through a Cohere-compatible rerank service, a local Transformers.js model, or an adapter of your own.
- **BM25 parameters.** You can set `k1` and `b` for an index, for a field, and for one search, and you can change an index's setting without a rebuild.
- **Changing an index's analysis.** You can give a live index a new language, stop-word set, or tokeniser, and the index keeps answering searches while the engine rebuilds its terms.

## Planned

The maintainers will build these items in the order of this list.

1. **Phrase search.** When a caller puts words in double quotes, as in `"olive oil"`, the engine will return only the documents that contain those words side by side and in that order, as [Meilisearch](https://www.meilisearch.com/docs/capabilities/full_text_search/getting_started/phrase_search) does with quoted words. For an index with `trackPositions` on, which is the default, the engine already stores the word positions that phrase search compares. Today the engine leaves no gap between the items of an array field. So that the engine matches each phrase inside one item, it will leave a gap of 100 positions between items, which means that it will rebuild every index that contains an array field. For an index with `trackPositions` off, the engine stores no positions, so it will refuse a phrase query on that index. The plan is in [#93](https://github.com/assetcorp/narsil/issues/93).
2. **An OpenAPI description of the HTTP API.** The repository holds no description of the HTTP API that tools can read today. An OpenAPI file will describe every route, so that anybody can generate a client in their own language. The plan is in [#147](https://github.com/assetcorp/narsil/issues/147).
3. **Disk-backed search.** Under a storage mode that you will choose for each index, the engine will keep part of the index in memory and read the rest from the index's files during each search, so that an index can grow larger than the memory of the node that stores it. The plan is in [#95](https://github.com/assetcorp/narsil/issues/95).
4. **Cluster backups to cloud storage.** A cluster node refuses `snapshot` and `restore` today, so a cluster has no backup. Replicas keep a cluster answering when a node fails, but a dropped index or a bad write reaches every replica. A cluster will save a snapshot of each index outside the cluster, in a store such as S3 or Google Cloud Storage, and it will restore an index from that snapshot. The plan is in [#148](https://github.com/assetcorp/narsil/issues/148).
5. **A React Native driver.** The engine answers searches in Node.js, Bun, Deno, and the browser today. With a React Native driver, the engine will answer searches in a React Native app, with or without Expo, searching keywords through its TypeScript code and vectors through the native search core, which the app's build will compile for iOS and Android. A file store on the phone will give the index a write-ahead log and will keep its full-precision vectors in files. The plan is in [#150](https://github.com/assetcorp/narsil/issues/150).
6. **Two-way device sync.** An app will be able to search and change an index on a device with no signal. A device will load a snapshot of the index first. After that, the server will send the device each document change that follows the device's saved position, with the document's vectors, over a WebSocket, while the device will send its own changes to the server. The developer decides what an index holds and who can read or write it. By default, the last write to arrive will win, although a developer can send a device's writes through their own backend so that the backend decides conflicts. When a device falls too far behind the server, it will load a fresh snapshot, as a device does under Sirannon's device sync. The maintainers will build device sync on the React Native driver and on cluster backups. The plan is in [#151](https://github.com/assetcorp/narsil/issues/151).
7. **Python and Go clients.** The only published client today is in TypeScript, so a Python or Go program has to write its own HTTP requests to reach a Narsil server. Each new client will offer the same operations as the TypeScript client. The plan is in [#152](https://github.com/assetcorp/narsil/issues/152).
8. **Popular query suggestions.** Today the engine's autocomplete suggests single words from the index's vocabulary. [Algolia's Query Suggestions](https://www.algolia.com/doc/guides/building-search-ui/ui-and-ux-patterns/query-suggestions) suggests whole queries, which it ranks by the number of times that people searched for them in the last 30 days, and it drops any query with fewer results than a minimum that you set. The engine will count the queries that callers send. On a schedule, a build step will then turn those counts into an ordinary Narsil index. You will also be able to fill that index by hand so that your users see suggestions from the first day of a new deployment. To count queries across a cluster, the maintainers will have to add a write path that merges counts from several nodes, since cluster mode has none today.
9. **A file store for browsers.** A file store on the browser's [origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system) will give an index in a browser the write-ahead log and the disk-backed search that an index on a server has.
10. **A conformance suite for the format.** With a shared set of format tests, the authors of any implementation will be able to check that it loads and saves `.nrsl` files exactly as the reference does.
11. **Keyword and hybrid search in the native search core.** The native search core is a C library. Today an implementation in any language searches vectors through that library, but it answers keyword queries in its own code. The core will answer keyword and hybrid queries too so that an implementation can call one search for every query. The TypeScript package will continue to contain its own keyword, vector, and hybrid search, because browsers and React Native apps search through that code. The maintainers will build this item before the second-language implementation, since without it the authors of that implementation will have to write keyword search again and match the reference on every query.
12. **A second-language implementation.** A second implementation in Go or Rust will load and save the same `.nrsl` files and pass the same format tests as the reference. The maintainers will choose between Go and Rust once they have weighed each language's runtime size, its concurrency model, and the libraries around it. A second implementation will show that programs in two languages can share one format.

## How to get involved

Read [CONTRIBUTING.md](CONTRIBUTING.md) to set up the repository, and look for issues with the `good first issue` label to make a first change. For any change to the `.nrsl` format, start from the specification in [`packages/spec`](packages/spec).

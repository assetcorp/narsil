# Roadmap

Narsil is a search engine that stores its indexes in the `.nrsl` binary format. A program in any language can load and save that format, because [`packages/spec`](packages/spec) specifies its layout. Any implementation that loads and saves the format counts as a valid Narsil. The TypeScript package is the reference implementation, so the maintainers check every other implementation against it.

The maintainers update this roadmap of planned work as the work proceeds. The roadmap contains no dates, since the plans in it can change. Open an issue to propose or discuss an item.

## Available now

- **Embedded engine.** The engine answers full-text, vector, hybrid, and geographic searches inside your application process, in Node.js, Bun, Deno, or the browser.
- **Single-node server.** A server serves the same engine through a REST API, along with a write-ahead log, bulk NDJSON import, and snapshots that you can restore.
- **The `.nrsl` format.** The engine saves and transfers every index in one binary format, so any runtime can load a file that another runtime writes.
- **Cluster mode.** Under `@delali/narsil/distribution`, the engine can operate across several nodes, with node roles, replication, and query routing between nodes that connect over an in-process transport, TCP with mutual TLS, or gRPC. Each replica writes every entry to its write-ahead log before it acknowledges the entry, and a search that fails on one copy of a partition goes to the next copy, so the cluster keeps every write that it acknowledges and keeps answering while one in-sync copy of each partition is alive.

## In progress
- **Pattern search.** A pattern field is a `verbatim` field or a `string` field with the `pattern` option. With pattern search, the engine tests the whole stored value of such a field against literal text, a wildcard pattern, or a regular expression, then keeps or drops each document by that test alone, without scoring it. The engine matches each pattern in its own syntax, without backtracking and within a cap on its work. When a pattern needs a feature outside that syntax, the engine raises an error. The specification, the documentation, and the TypeScript code for pattern search are on the main branch, although no published release includes them yet.

## Planned

The maintainers will build these items in the order of this list.

1. **Synonyms.** With a synonym set, the engine will return the documents that contain 'jacket' for a search on 'coat'. The engine will expand each query word into its synonyms when it answers a search, so a caller can replace a set without a rebuild. The first version will cover single-word synonyms, because the engine can match a multi-word synonym such as 'progress bar' only once it supports phrase search. The plan is in [#92](https://github.com/assetcorp/narsil/issues/92).
2. **Phrase search.** When a caller puts words in double quotes, as in `"olive oil"`, the engine will return only the documents that contain those words side by side and in that order, as [Meilisearch](https://www.meilisearch.com/docs/capabilities/full_text_search/getting_started/phrase_search) does with quoted words. For an index with `trackPositions` on, which is the default, the engine already stores the word positions that phrase search compares. Today the engine leaves no gap between the items of an array field. So that the engine matches each phrase inside one item, it will leave a gap of 100 positions between items, which means that it will rebuild every index that contains an array field. For an index with `trackPositions` off, the engine stores no positions, so it will refuse a phrase query on that index. The plan is in [#93](https://github.com/assetcorp/narsil/issues/93).
3. **Disk-backed search.** Under a storage mode that you will choose for each index, the engine will keep part of the index in memory and read the rest from the index's files during each search, so that an index can grow larger than the memory of the node that stores it. The plan is in [#95](https://github.com/assetcorp/narsil/issues/95).
4. **BM25 parameters at query time.** The engine scores a full-text search with BM25 under the `k1` and `b` that you set when you create an index. The engine computes every score at query time from the term frequency, the field length, and the average field length that it already stores, so a caller will be able to pass a different `k1` and `b` with each query. You will also be able to change an index's stored pair without a rebuild.
5. **Re-analysis under a new analysis config.** The engine already re-analyses a stale index in place, one partition at a time, from its stored documents, while it leaves the vectors as they are. Today the engine marks an index stale only when a language module's revision changes, since you set an index's stop words, tokeniser, and language once, when you create it. The server's `POST /indexes/{name}/_rebuild-analysis` endpoint rebuilds an index under the settings that it already has. Under this item, you will be able to give an existing index a new stop-word set, tokeniser, or language, after which the engine will rebuild the index under the new settings.
6. **An Expo driver.** The engine answers searches in Node.js, Bun, Deno, and the browser today. With an Expo driver, the engine will answer searches in a React Native app, searching keywords through its TypeScript code and vectors through the native search core, which the app's build will compile for iOS and Android.
7. **Device sync with a change feed.** A device will load a snapshot of an index first. After that, the server will send the device each document change that follows the device's saved position, with the document's vectors, over a WebSocket. Sync will work in one direction, from the server to each device. When a device falls too far behind the server, it will load a fresh snapshot, as a device does under Sirannon's device sync. The maintainers will build device sync on the Expo driver and on the snapshots that the server already serves.
8. **Reranking.** The engine will reorder the top results of a query with a second model, such as a cross-encoder, which scores the query and each candidate document together. Three other engines offer reranking: Elasticsearch through its [`text_similarity_reranker` retriever](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/text-similarity-reranker-retriever), Vespa in a [global ranking phase](https://docs.vespa.ai/en/phased-ranking.html) that covers the 100 best hits by default, and Weaviate through [reranker modules](https://docs.weaviate.io/weaviate/concepts/reranking) for keyword, vector, and hybrid search. Today the engine ranks every result by its keyword, vector, or hybrid score alone. The engine passes the `afterSearch` plugin hook a copy of the hit list, so if you reorder the hits inside that hook, the caller receives them in their first order. Until the maintainers build this item, you will have to rerank results in your own code after each query. Before they build it, the maintainers will settle four questions:
   - What shape will the query option take?
   - Will the model come from an adapter, as an embedding model does?
   - How will reranking combine with hybrid fusion and with pagination?
   - Which node will score the candidates when the coordinator sends a query to several nodes?
9. **Keyword and hybrid search in the native search core.** The native search core is a C library. Today an implementation in any language searches vectors through that library, but it answers keyword queries in its own code. The core will answer keyword and hybrid queries too so that an implementation can call one search for every query. The TypeScript package will continue to contain its own keyword, vector, and hybrid search, because browsers and React Native apps search through that code. The maintainers will build this item before the second-language implementation, since without it the authors of that implementation will have to write keyword search again and match the reference on every query.
10. **A second-language implementation.** A second implementation in Go or Rust will load and save the same `.nrsl` files and pass the same format tests as the reference. The maintainers will choose between Go and Rust once they have weighed each language's runtime size, its concurrency model, and the libraries around it. A second implementation will show that programs in two languages can share one format.
11. **A conformance suite for the format.** With a shared set of format tests, the authors of any implementation will be able to check that it loads and saves `.nrsl` files exactly as the reference does.
12. **Popular query suggestions.** Today the engine's autocomplete suggests single words from the index's vocabulary. [Algolia's Query Suggestions](https://www.algolia.com/doc/guides/building-search-ui/ui-and-ux-patterns/query-suggestions) suggests whole queries, which it ranks by the number of times that people searched for them in the last 30 days, and it drops any query with fewer results than a minimum that you set. The engine will count the queries that callers send. On a schedule, a build step will then turn those counts into an ordinary Narsil index. You will also be able to fill that index by hand so that your users see suggestions from the first day of a new deployment. To count queries across a cluster, the maintainers will have to add a write path that merges counts from several nodes, since cluster mode has none today.
13. **A browser file store.** A file store on the browser's [origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system) will give an index in a browser the write-ahead log and the disk-backed search that an index on a server has.
14. **A phone file store.** A file store on a phone will give an index in a React Native app the write-ahead log and the disk-backed search that an index on a server has. The store will call fsync through its own native code, since `expo-file-system` offers no fsync.

## How to get involved

Read [CONTRIBUTING.md](CONTRIBUTING.md) to set up the repository, and look for issues with the `good first issue` label to make a first change. For any change to the `.nrsl` format, start from the specification in [`packages/spec`](packages/spec).

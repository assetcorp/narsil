# Every language searches vectors through one native core in C

Narsil searches its vector graph through a native search core written in C, which every language implementation loads wherever the platform can load native code. We decided this because a C search of the same index returns the same answers in less than half the time that the TypeScript search takes.

On 100,000 DBpedia vectors of 1,536 dimensions with 4-bit codes, the TypeScript implementation takes 445 µs per query on one thread of an Apple M3 Pro and 498 µs inside the benchmark's Linux container. A query makes about 1,900 comparisons, each of which is a call from JavaScript into a WebAssembly kernel. A C search that follows the same steps takes 183 µs on the host and 201 µs in the container. It returns the same ten results and the same score bits as the benchmark server on all 5,000 DBpedia queries, all 323 NFCorpus queries, and all 300 SciFact queries, both at 4 bits and at full precision. When Node loads it as a Node-API addon in eight worker threads over one shared copy of the index, a query takes 280 µs in the container while eight plain C threads take 289 µs, so the addon adds no time that we could measure. A call from Node into the addon takes 78 ns. WebAssembly cannot match those figures, since 94 µs of the saving comes from fetching the records of a node's unvisited neighbours before the comparisons start, and WebAssembly has no prefetch instruction.

The core searches the graph for a query. It also finds the candidates for a new vector during placement, which is the same walk at the construction effort. It handles every code size, every metric, and tombstones. While another thread places vectors, the core applies the same per-node version checks and the same graph lock as the TypeScript search does, which adds 1.9 µs to a query when no thread is writing and 4.0 µs when four threads are. Link selection, pruning, and the locked writes of placement remain in the host language, although the interface must allow them to move into the core later. The TypeScript implementation keeps its WebAssembly search because a browser cannot load C. That search remains the reference for the spec, and a runtime falls back to it wherever the core has no binary for the platform or the processor lacks an instruction that the core needs.

The core and the WebAssembly search must return the same results bit for bit. A job in continuous integration must prove that on every platform that the core is built for, by searching one fixture index through both. Matching the WebAssembly arithmetic adds 4.5 µs to a query. Both searches change their full-precision dot product from one running sum to four, because a single sum forces every addition to wait for the one before it. On full-precision DBpedia the C search takes 824 µs with one sum and 623 µs with four, while JavaScript takes 956 µs. Four sums alter the last digits of a score, and they altered the ten results of 2 queries in 5,000, which harms no stored data because no file holds a score.

The format stores a 4-bit code as two levels per byte and a 2-bit code as four levels per byte, both on disk and in memory, in place of one bit plane per bit. The C search is 39 µs per query faster on that layout. Because disk and memory share one layout, a load or a checkpoint can copy the records without converting them. The estimate adds up integer products of levels, so the packing changes no score. We change the format now because Narsil has not reached 1.0 and has one user.

The core has its own package, its own version, and a plain C interface that contains no Node type. The Node-API layer is a thin shim beside the core, and an implementation in another language would write its own shim. The project publishes prebuilt binaries per platform in the way that sirannon-db publishes its extension, with no install script. The first targets are macOS and Linux on arm64 and x64, for both glibc and musl, and Windows follows once a continuous integration runner proves that the addon links there. The core checks every ordinal that it takes from the graph against the node count, because a corrupt ordinal would otherwise crash the whole server, whereas JavaScript would raise an error. A sanitiser job searches the fixture index on every change.

## Considered options

We first planned to move the comparison, the query code, and the walk into WebAssembly. That plan needs a second memory for the graph, which Safari does not support, and its dot-product instruction is available only behind relaxed SIMD. We chose C over Rust because the author already writes C. C++ would still have to expose a C interface so that Node, Go, and Rust could bind to it, and it depends on a runtime library that differs between glibc, musl, and Windows. A call through `node:ffi` takes 365 to 373 ns where a call into the addon takes 78 ns, and `node:ffi` is experimental and first appeared in Node 26.1, while the package supports Node 22. Splitting the index into four graphs that four threads search at once answers one query in 137 µs, but eight threads then complete 11,416 queries per second where one graph completes 28,848. Keeping bit planes on disk would mean converting the records at every load and every save, which takes about 150 ms per 100,000 vectors of 1,536 dimensions, and every language would have to hold two layouts, the conversion, and the tests for both.

## Consequences

The layout of the graph, the records, and the lock words in memory becomes a contract, because an implementation in another language has to build the memory that the core searches. That layout therefore has to be written down as carefully as a file format. The kernels that we measured use Arm instructions, so x86-64 needs its own kernels, and we have not measured their speed. We have also not measured the WebAssembly kernel on two levels per byte; if it proves slower, a browser would convert the records to bit planes as it loads them. Once the format changes, a reader rejects every vector file that holds bit planes. The core's memory is outside the JavaScript heap, so the memory estimator must count it when the core is the search backend, and it must count the WebAssembly search's memory when the core is not. An implementation in another language no longer has to write a vector search, but it has to load one native dependency and keep it at the same version as its own code.

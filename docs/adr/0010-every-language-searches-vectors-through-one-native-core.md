# Every language searches vectors through one native core in C

Narsil searches its vector graph through a native search core written in C, which every language implementation loads wherever the platform can load native code. A search in TypeScript crosses from JavaScript into a WebAssembly kernel once per comparison, and a single query makes thousands of comparisons, so those crossings take most of the query. The core compares a whole neighbour list inside one call, and it prefetches the records of a node's unvisited neighbours before it compares them, where WebAssembly has no prefetch instruction at all.

The core performs seven operations, which the spec names `search`, `score`, `place`, `remove`, `compact`, `calibrate`, and `quantise`. It searches the graph for a query, and it scores full-precision vectors both for the re-check of a quantized search and for every scan of a field that holds no graph. It places a new vector, which means that it finds the candidates, selects the diverse neighbours, writes the lists under the node locks, and prunes each neighbour that is over its limit. It marks a removed node, it takes every marked node out of the graph during compaction, and it computes the centroid and writes the code records of a quantized field. It handles every code size, every metric, and tombstones. The core reads and writes each node's list under the lock protocol of the spec, so a thread may place vectors while another thread searches. The host language keeps three duties, which are growing the shared memory, drawing the random top layer of a new node, and encoding the file formats. C cannot grow a JavaScript `SharedArrayBuffer`, so `place` returns `needsRoom` where a region is full, and the host then grows the region and calls `place` again.

The core maps each vector file of a `disk` index into memory, as Qdrant maps its on-disk vector storage, and it advises the operating system that the reads are random, which is Qdrant's default advice. The host detaches every thread from a file before it deletes that file, because Windows refuses to delete a file while a process maps it. A process that touches a mapped page beyond the end of a truncated file ends with a bus error on macOS and Linux, and we accept that risk, because Narsil writes a vector file once and never changes it afterwards.

The TypeScript implementation keeps every one of the seven operations in its own code, because a browser and a React Native app cannot load C, and that code stays the reference for the spec. A runtime falls back to it wherever the core has no binary for the platform, wherever the core cannot serve the index, and wherever an operator asks for the WebAssembly search. A quantized index takes its centroid again whenever `optimize` rebuilds the graph, as Lucene recomputes its centroid when it merges segments, while `compact` leaves the centroid alone so that its time stays bounded by the tombstones.

The core and the WebAssembly search must return the same results bit for bit, which a job in continuous integration proves on every platform that the project publishes, by building, searching, and compacting one fixture index through both. The two must also write the same graph and the same code records for that index. Both searches add up their full-precision dot product in four running sums, because a single sum makes every addition wait for the one before it. Four sums alter the last digits of a score, which harms no stored data, because no file holds a score.

The format stores a 4-bit code as two levels per byte and a 2-bit code as four levels per byte, both on disk and in memory. One layout for both means that a load or a checkpoint copies the records without converting them. The core estimates a distance by adding up integer products of levels, so the packing changes no score. We change the format now, because Narsil is before 1.0 and has one user.

The core has its own package, its own version, and a plain C interface that holds no Node type. The Node-API layer is a thin shim beside the core, and an implementation in another language would write its own shim. The project publishes a prebuilt binary per platform in the way that sirannon-db publishes its extension, with no install script. The targets are macOS, Linux, and Windows on arm64 and x64, with a glibc build and a musl build for Linux. On Windows the shim resolves each Node-API function from the host process as it loads, so one binary serves `node.exe` and any program that embeds Node. The core checks every ordinal that it takes from the graph against the node count, because a corrupt ordinal would otherwise crash the whole server, where JavaScript would raise an error. A sanitiser job performs every operation on a fixture index on every change, and it places vectors from two threads while two more threads search.

## Considered options

We first planned to move the comparison, the query code, and the walk into WebAssembly. That plan needs a second memory for the graph, which Safari does not support, and its dot-product instruction is available only behind relaxed SIMD. We chose C over Rust because the author already writes C. C++ would still have to expose a C interface so that Node, Go, and Rust could bind to it, and it depends on a runtime library that differs between glibc, musl, and Windows. A call through `node:ffi` takes several times as long as a call into a Node-API addon, and `node:ffi` is experimental and first appeared in Node 26.1, while the package supports Node 22. Splitting the index into four graphs that four threads search at once answers one query sooner, although the process then completes fewer queries per second. Keeping bit planes on disk would mean converting the records at every load and at every save, and every language would have to hold two layouts, the conversion, and the tests for both.

## Consequences

The layout of the graph, the records, and the lock words in memory becomes a contract, because an implementation in another language has to build the memory that the core searches. That layout therefore has to be written down as carefully as a file format. The kernels that we measured first use Arm instructions, so x86-64 has its own kernels, which the identity job proves on the x64 runners. A vector file written before this change holds bit planes, and `decodeVectorIndexParts` raises `ENVELOPE_VERSION_MISMATCH` for it. The core's memory is outside the JavaScript heap, so the memory estimator counts it where the core is the search backend, and it counts the WebAssembly search's memory where the core is not. An implementation in another language no longer has to write a vector search, although it has to load one native dependency and keep it at the same version as its own code.

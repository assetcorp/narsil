# Full-precision vectors stay on disk and the graph grows from codes

Before this decision, the engine kept every full-precision vector in memory, so a million DBpedia vectors of 1,536 dimensions took 6.1 GB of floats before any code, graph, or text. No code size could bring that figure down, since it counts the floats alone. The 1-bit codes for the same million vectors take 0.2 GB, while the graph takes 0.14 GB, so both of them can stay in memory while the floats stay on disk. However, Narsil also runs embedded and in a browser, where it has no file that it can read by position.

We have decided that every index has a storage setting with the values `memory` and `disk`. When the setting is absent, an index with filesystem durability uses `disk`, while every other index uses `memory`. The engine rejects a config that asks for `disk` without a filesystem, with `CONFIG_INVALID`. For a `disk` index, the engine keeps the codes and the graph in memory but reads a full-precision vector from the vector file by position whenever a search re-scores a candidate or a caller fetches a document. For every quantized index, in either mode, the engine places a new vector in the graph by scoring it as a query against the codes of its neighbours. The engine therefore reads a neighbour's floats during a build only where that neighbour holds no code. The engine writes the vectors as fixed-size float32 records at the end of the payload, in files of at most 65,536 vectors, so a reader can compute where a vector lies without decoding the file.

## Considered options

Keeping the floats in memory and shrinking only the codes can save at most a fifth of the memory, because with 8-bit codes the floats make up four fifths of it. A graph built from floats read off disk will need the vector of every neighbour that the engine compares a new vector against, which can come to thousands of positional reads per insert at the default `efConstruction` of 200, on top of the thirty that a query makes. A setting that the engine chooses on its own, with no override, takes the choice away from a deployment that needs to pin a small index in memory for speed or to push a large one to disk. Splitting the vector files by byte size, in place of a vector count, will make the position of a vector depend on the file that holds it.

## Consequences

For a query at `k` of 10 with a 3x rescore, the engine reads 30 vectors from the vector file. Each read took 0.7 to 0.8 µs from the file cache on an Apple M3 Pro in September 2026. No measurement exists yet for a read that misses the file cache, which matters because high disk latency can make the re-scoring step a bottleneck. The benchmark harness measured a graph built from 4-bit codes at 1,536 dimensions, with a full-precision rescore, in its run of 28 September 2026. It recorded an ann_recall@10 of 0.9919 on the DBpedia entities 100K set at an `efSearch` of 128, and 0.9942 on the 1M set at an `efSearch` of 384, both above its target of 0.99. With that target met, the engine builds the graph of every quantized index from codes, and for the same reason an index with filesystem durability uses `disk` by default. An index in a browser and an embedded index without durability use `memory`. A browser index will be able to use `disk` once the engine reads the Origin Private File System by position. At 1,536 dimensions, a full vector file holds about 0.4 GB of floats, far under the 4 GiB that the envelope header can describe. Nothing caps the dimension of a vector field, however, so a field wider than about 14,500 dimensions with 4-bit codes fills a file of 65,536 vectors past that limit, at which point the engine fails the save with `PERSISTENCE_SAVE_FAILED`. The engine rejects a vector file in an earlier layout with `ENVELOPE_VERSION_MISMATCH`, because the envelope specification requires a reader to reject an earlier layout until its compatibility rules take effect at 1.0.

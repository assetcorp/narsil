# Narsil matches patterns in its own syntax with an engine that never backtracks

Narsil finds text inside field values through three tests on a pattern field: `contains` for literal text, `wildcard` for a pattern of `*` and `?` that has to match the whole value, and `regex` for a regular expression in a syntax that the spec defines. Each implementation matches that syntax with an engine of its own that never backtracks, within limits on the size of every pattern and on the work of every search. When we made this decision, the only filters that looked inside a value were `startsWith` and `endsWith`, both of which check the value of every document.

The engine never backtracks, because a backtracking engine can take time that grows exponentially with the length of the text for some patterns, as V8's engineers describe for JavaScript's `RegExp`. On 2 July 2019, Cloudflare's firewall engine backtracked on one pattern until the use of the processors that serve HTTP traffic across Cloudflare's network reached nearly 100%, which caused an outage of 27 minutes. Cloudflare then moved to the RE2 and Rust regex engines, which guarantee a bound on their matching time. V8 has a linear-time engine of its own; however, it turns that engine on only under command-line flags, which no web page can set.

A regular expression matches anywhere in the value, while the anchors `^` and `$` always stand for the start and the end of the whole value. Grep and JavaScript also search for a match anywhere in the text. The syntax consists of literal characters with `\` as the escape, `.` for any single code point including a line break, sets such as `[a-z]` and `[^0-9]`, the classes `\d`, `\w`, and `\s` over ASCII alone, `|` for either side, brackets for grouping, the repeats `*`, `+`, `?`, `{n}`, `{n,}`, and `{n,m}`, the anchors, the word edge `\b`, and number ranges such as `<1-65535>`. A number range has bounds of at most 15 digits, which every language stores exactly as an integer. A range match has no leading zeros unless both bounds have the same number of digits, in which case every match has that many digits. The engine raises an error for back-references, lookaround, and possessive repeats, which RE2, built to withstand denial-of-service patterns, also leaves out. It also raises an error for lazy repeats, because a lazy repeat changes nothing in a test whose outcome is yes or no. An inline flag is an error too, because case matching follows the `caseFold` setting. A Unicode property class such as `\p{L}` is an error as well, because supporting it means that every implementation has to include category tables pinned to one Unicode version, while the only Unicode table in the spec today is the case fold.

The engine builds its deterministic machine step by step as it matches, caching the states that it builds in at most 1 MB of memory. Whenever the cache is full, the engine empties it and continues, as RE2 does, so the matcher memory of one search never passes 1 MB. Each cached state consists of at most 2,048 pattern positions of 4 bytes each, which is 8 KB, so the cache has room for at least 128 states. A pattern can have at most 1,024 code points and at most 32 levels of nested brackets. Before it builds anything, the engine works out how many states a pattern takes once its counted repeats expand, and it raises an error above 2,048 states. The 13-character pattern `a{1000}{1000}` expands to a million states, so the engine raises an error for it. A 15-digit number range expands to 445 states and the range from 1 to 4,294,967,295 expands to 340, so both fit inside the limit.

The engine counts every matcher step that it performs and every shortlist entry that it fetches in a search, and it stops the search with an error once the count passes the work cap. The cap defaults to 25 million units, which comes to 0.9 seconds at the slowest rate that we measured, 36 ns per step on an Apple M3 Pro with other applications open. That is about a fifth of the 5 seconds that a cluster coordinator allows each node to answer. An operator can change the cap through an engine setting, because checking long values can exceed the default. An operator can also turn regular expressions off for every client of a server.

The engine keeps an index of every run of three characters in the folded value of each pattern field, together with a compact list of the 32-bit numbers of the documents whose value contains that run. It saves that index with the rest of the partition as an optional entry beside the other field indexes. For an index without a pattern field, the engine builds and writes no such entry, so it writes the same bytes as before for every existing index. It builds the shortlist for a search from the rarest runs in the pattern and checks every candidate against the whole pattern, so the shortlist changes how long a search takes but not which documents match. On 100,000 DBpedia article texts and 200,000 file paths, that index occupies 3.0 bytes per character of text once a segment is frozen and 4.7 to 6.0 bytes per character while the segment is still growing. For the article texts, that comes to 91 MB frozen and 163 MB growing, against 586 MB for a Narsil index of the same articles' titles and texts.

Matching is case-sensitive unless the caller sets `caseFold` on a test, in which case the engine compares text under the spec's full Unicode case fold. The engine uses its one index over folded values for both modes. A caller can also set a `tolerance` of up to 2 on an `eq` test of a pattern field. The engine measures that tolerance with the bounded Levenshtein distance that the spec defines for typo tolerance, so a swap of two neighbouring characters counts as two edits. A value within k edits of the query shares at least one run with any set of k × (2 + f) + 1 distinct runs of the query, where f is the number of characters in the longest case fold among the query's characters, so the engine fetches only the lists for the rarest k × (2 + f) + 1 runs. Across 1,980 test queries on 100,000 article titles and 200,000 file paths, the engine found the original value of every edited query. A query over the paths took 0.7 ms with one typo and 1.5 ms with two.

## Considered options

A syntax in which every pattern has to match the whole value, with no anchors, differs from grep and JavaScript. The syntax has no 'not' operator, because the engine can complement a pattern only through a deterministic machine whose size can grow exponentially with the pattern. It has no 'and' operator either, because each 'and' multiplies the size of the matching machine by the size of the pattern on its other side. JavaScript's `RegExp` backtracks. It also supports back-references and lookaround, which RE2 leaves out, so the same pattern can match differently from one implementation to the next. The `re2js` package matches in linear time, but it supports the whole RE2 syntax, so Narsil still needs a parser of its own for everything outside the spec. Using the package also adds a second runtime dependency next to `@msgpack/msgpack`. We named the whole-value test `wildcard` and not `glob`, because the shell's `*` never matches a `/` in a file name, while ours matches any character. Listing each distinct value and then its documents lets the engine check a shared value once. In that layout, however, the engine keeps a JavaScript `Set` for every value and stores every value a second time, as the enum index does, so it stores a field of unique log lines twice.

## Consequences

The authors of every implementation have to write its parser, its matcher, and its shortlist from the spec. To check the TypeScript engine, a test compares the engine's answers with RE2's answers on randomly generated patterns. We add RE2 only as a test dependency, so no user of Narsil installs it. The characters `<` and `>` mark a number range in a pattern, so a caller who wants to match either one literally has to put a backslash before it. The engine builds its shortlist from runs of three literal characters, so for a pattern without such a run, such as `\d{4}-\d{2}-\d{2}`, it has to check every value of the field. On the 100,000 article texts, for example, the engine passes the default cap after checking about 75,000 of them. The browser build is a single file with no code splitting, so the engine has no separate file from which it can load the pattern code on demand. Narsil therefore publishes the pattern code as a separate import, so that a bundler includes it only for an app that imports and registers it. In Node, however, each worker thread loads the pattern code by itself when an index has a pattern field.

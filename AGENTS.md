# Working in this repository

`packages/spec` holds the cross-language contract, which outranks the TypeScript code. `packages/ts` is the reference implementation, so any port to another language must match both.

Read the file that you're editing and follow what it already does. The rules below cover what that reading leaves out.

## Rules

- Re-read and apply the user's writing guidelines fully, if available, whenever you are writing TS-Doc or any prose in the repo.
- Leave `packages/spec` alone. The developer owns every spec change and makes it directly. When your work needs a different header field, envelope version, payload encoding, client-facing error code, or replication invariant, say so and wait for their decision. Write no code against a spec change they have not approved.
- Keep every source file under 400 lines. Measure a file when you touch it, and split it before your change pushes it over. Turn a module that outgrows one file into a directory with an `index.ts` that re-exports it, and drop the module prefix from each filename inside. Copy `src/core/partition/` or `src/engine/mutations/`. The limit covers source only, so tests and every file that a generator writes are exempt, and a generator writes each file whole however long it grows. `src/languages/` is exempt as well, because each module ports a published stemmer and a reader checks those line by line against the reference. `packages/ts/wasm/` is exempt too, because `wasm/build.ts` reads `simd-distance.wat` as one file.
- Put every tuning value, meaning a threshold, an interval, a size, or a retry budget, in its directory's `constants.ts`, and leave a byte layout, a wire tag, and a format version beside the function that decodes them. Name a constant `DEFAULT_X` where a config field overrides it, `MAX_X` or `MIN_X` where the engine throws a `NarsilError` beyond it, and a plain name where nothing overrides it, ending a duration in `_MS` and a size in `_BYTES`. A `constants.ts` must hold literals alone and import nothing at runtime beyond another `constants.ts`, so a bundler can drop what a caller never imports, and importing one adds no platform code to a bundle. The 400-line limit skips a `constants.ts`, which must stay one file however many values it holds.
- Keep everything tree-shakeable. A bundler must be able to drop any capability the caller never imports, so add no barrel that pulls siblings in, and register no optional capability at module load. `src/languages/registry.ts` holds English alone for exactly this reason, and a caller imports and registers any other language itself. Registering all of them there would pull every stop word list and every stemmer into every bundle, so leave that file as it is and make each new language reachable by direct import.
- Throw a `NarsilError` carrying a code from `ErrorCodes` in `src/errors.ts`, and let it propagate unchanged, because its code is what the server maps to an HTTP status. Add every new code in `ErrorCodes` or `ServerErrorCodes` to `STATUS_BY_CODE` in `src/server/errors.ts`, or the server answers 500. The `ClientErrorCodes` stay out of that map, because the HTTP client raises those after the response and no request can arrive under one.
- Leave `VERSION` in `src/index.ts` alone unless the developer asks for a new value. `serialization/envelope.ts` writes it into the engine-version bytes of every `.nrsl` file, where the format gives each part a single byte and nothing reads it back. It records the engine, and it carries no relation to the published package version, so never sync it to `package.json` and never bump it alongside a release.
- Put every test under its package's `src/__tests__/`, mirroring the directory it covers. All three packages collect `src/**/__tests__/**/*.test.ts`, and `packages/ts` adds `benchmarks/__tests__/`, so a test beside its source never runs.
- Write no unit tests, only integration tests and end-to-end tests. An integration test uses real resources, and an end-to-end test goes through the real routes. No test uses `vi.mock`, `vi.spyOn`, or fake timers.
- Test each feature only through integration tests on the public `Narsil` API and end-to-end tests on the HTTP server and the published client, written from the side of a hostile user who sends malformed input, reaches and crosses every limit, chooses bad settings, and mixes writes with restarts, snapshot restores, and worker copies. Check every answer against an independent oracle that shares no code with the engine, because a test that reuses the engine's own logic can pass while the engine is wrong.
- Never propose refusing, narrowing, or deferring a capability because implementing it properly is harder. Read how established engines solve it and what this repository already does, then propose that. `registerEmbeddingAdapter` in `src/narsil/operations.ts` takes a name because an instance survives neither a worker boundary nor a restart, and a custom tokenizer, a stop word function, and a language module all need that same treatment.
- Write no `any`, no non-null assertion, and no `@ts-ignore` or `@ts-expect-error` under `packages/ts/src`. The package has none today; narrow the type instead.
- Write a TSDoc comment on every member of `Narsil` and on every export that reaches a published type file, meaning one that a module in the `entry` lists of `tsup.config.ts` re-exports, directly or through a chain, because `tsup` carries the comment into `dist/*.d.ts`, which an editor shows on hover and the documentation site publishes. An export that only other modules under `src/` import needs none, `@internal` tag or not; when unsure, build and search every `.d.ts` under `dist/` for the name, and treat the API reports under `etc/` as the final word, because the build fails on a reported declaration without a release tag. Open with what the caller gets, keep the prose plain and British, and describe each parameter and the return value. Link another symbol with `{@link Narsil.insertBatch}`, which resolves inside this package, and paste no URL. That TSDoc is the only comment the repository carries: a non-exported function, an export that no entry reaches, a catch block, a test, a harness, and a fixture carry none, whatever the reason seems to be.
- Install with `pnpm add -E` from inside the target workspace, and leave the `dependencies` and `devDependencies` blocks alone otherwise.
- Run `pnpm nx run narsil-ts:lint`, `pnpm nx run narsil-ts:typecheck`, `pnpm nx run narsil-ts:build`, and `pnpm nx run narsil-ts:test` before you report a change done. Add the `narsil-certutil` and `narsil-embeddings-transformers` targets when you touch those packages, add the `generate`, `lint`, `typecheck`, and `test` targets of `narsil-python` and `narsil-go` when you touch `packages/python`, `packages/go`, or a route in `openapi.json`, run `pnpm --filter @delali/narsil-native-build lint` and `pnpm --filter @delali/narsil-native-build test` when you touch `packages/native`, and follow `packages/ts/src/languages/README.md` when you touch `src/languages/`.
- As the coordinating agent, research how established products solve every question that a session asks you and read every part of the code that it touches before you answer, and assume nothing.

## Gotchas

- **Every worker loads its entry from `dist/`.** `workers/factory.ts`, `vector/search-pool/worker-entry.ts`, and `persistence/durability/checkpoint-worker-entry.ts` each rewrite their own `/src/` path to a `/dist/*.mjs` path through `resolveWorkerEntry` in `workers/entry-point.ts`. Each has a `.react-native.ts` variant without `import.meta`, because Hermes refuses to compile a bundle that holds it. Build before you run a test that loads worker copies, searches vectors off-thread, or offloads a checkpoint.
- **Worker copies are on by default everywhere but a browser.** `createNarsil()` with no `workers` setting loads a copy of any index onto every worker once it holds 1,000 documents, so a test that inserts that many documents spawns threads and needs `dist/` built. Pass `workers: { enabled: false }` in a test whose subject is the main copy alone.
- **Node builtins break the browser bundle.** Lint, typecheck, and the tests all pass when a file under `src/` imports `node:fs`; only `scripts/check-browser-bundle.mjs` reports it, and it walks the import graph from `dist/index.browser.mjs` and `dist/client.mjs`, which `pnpm build` produces before running the check. Add every new browser-facing entry to that list. Route Node-only code through a `#platform/*` subpath declared in the `imports` block of `packages/ts/package.json`, with a `.browser.ts` variant beside the Node one.
- **The build fails when a browser app without the optional features grows.** The same script bundles `scripts/browser-bundle-app.mjs`, an app that imports neither pattern search nor partial-word search, that declares no vector field, that sets no durability, that quotes no phrase, and that stores no object value. The script fails when the chunks that this app downloads at start-up pass the gzipped size in `scripts/browser-bundle-size.json`, and it fails when those chunks hold `src/core/partition/phrase-matching.ts`, `src/search/phrase-analysis.ts`, `@msgpack/msgpack`, a module that `src/serialization/msgpack-leaf.ts` exports, or any file under `src/vector/` or `src/persistence/durability/` other than a `constants.ts`. Put code that only an optional feature calls behind that feature's registered module or behind a dynamic `import()`, as `workers/vector-code.ts` does for the vector code, `search/phrase-code.ts` does for the phrase code, and `serialization/msgpack-code.ts` does for the MessagePack code, and run `pnpm bundle-size:write` only for growth that you mean to keep.
- **A lazily loaded chunk holds every module that it uses.** The same script fails when a chunk that only a dynamic `import()` reaches imports another chunk or holds a dynamic `import()` of its own, because Rollup and Vite can then make an app that awaits the engine at the top level of its entry wait forever. Import a module of the same chunk statically, and have the host pass the lazily loaded module any other code through its bindings, as `serialization/gzip-code.ts` does with a loader function for gzip.
- **`narsil-ts:lint` checks `src/` only.** That target skips `packages/ts/scripts/`, `packages/ts/wasm/`, and `packages/ts/benchmarks/`. `typecheck:tooling` type-checks those three, and root `pnpm format` formats them.
- **The default test target skips the slow suites.** `narsil-ts:test` excludes `vector/recall.test.ts`. Recall runs under `test:recall`, etcd integration under `test:etcd` against a live endpoint in `NARSIL_ETCD_ENDPOINT`, and embedding end-to-end under `test:embeddings` with `NARSIL_TEST_EMBEDDINGS=1`. The file-backed memory test maps vector files through the native core, so it runs under `test:file-backed-memory` in `native-core.yml` with `NARSIL_NATIVE_CORE_PATH` set. Continuous integration runs recall and embedding only when a pull request or a push to `main` touches their paths.
- **A pull request splits `narsil-ts:test` across four jobs in `ci.yml`, and a push to `main` splits it across four jobs in `publish.yml`, each limited to 10 minutes.** A pull request runs them on Node 24, and a push runs them on Node 22, the oldest version that the package supports. When a job nears that limit, shorten its slowest test file or add a job to the matrix in that workflow, and remember that a new job in `ci.yml` renames the required `Tests N of 4` checks, so the branch ruleset has to change with it. The two `Cluster Tests` jobs in `ci.yml` run `test:cluster` and `test:faults` side by side on a pull request that touches `src/distribution/`, and they stay out of the required checks because a skipped matrix never reports its check names, so a required one would wait forever on any other pull request. On a push to `main`, two more jobs in `publish.yml` split `test:cluster` between them, and the first of the two also runs `test:etcd` and the container-memory suite, which otherwise runs only in a release. `ci.yml` runs none of the TypeScript suite on a push, because the prerelease in `publish.yml` publishes only after the suite passes, and a job can wait only on jobs in the same workflow.
- **A language change needs steps the usual four targets do not cover.** Changing analysis means bumping the module's revision, adding a language means writing the fixture the coverage gate requires, and an alphabet with lookalike letters means recording a substitution count. `packages/ts/src/languages/README.md` lists every command, when to run it, and which ones continuous integration enforces. Read it before you edit `src/languages/`.
- **A pull request and a push to `main` test each changed language once on each operating system, and a release tests it on every platform.** `ci.yml` calls `rust.yml`, `go-engine.yml`, `python-engine.yml`, `native-core.yml`, and `clients.yml` as reusable workflows, and each one picks its matrix from `github.event_name`. On a pull request and on a push, Go, Rust, and Python each get Linux x64, Windows x64, and macOS on Apple silicon, Go and Python also get their oldest supported versions on Linux, and a job splits into parts only where one runner would need more than 10 minutes. GitHub runs 5 macOS jobs at a time on this account, so a push to `main` must start 5 at most across `ci.yml` and `publish.yml`: Go and Rust take 2 each, and one job builds and tests the Python wheel. The C lint checks the macOS headers from any host, so it runs on Linux in 2 parts for a pull request and a push and on macOS in one job for a release, and `publish.yml` passes `run-lint: false` to `native-core.yml` on a push, because `ci.yml` lints the C code whenever its files change. `native-core.yml` builds every core except the two macOS ones on a push, because a prerelease publishes no macOS package, so `@delali/narsil@next` searches through WebAssembly on a Mac. Every other event, which includes each release from `publish.yml`, gets every platform, the oldest supported versions, musl, Arm, and every wheel, so a release publishes a package only after its full matrix passes. `publish.yml` alone calls `react-native.yml`: a push builds the Android apps before the prerelease of `@delali/narsil-react-native`, and a release builds the iOS apps as well. `engine.yml` builds the TypeScript engine and fetches the conformance dataset once per run, and every other job downloads the `narsil-ts-dist` and `conformance-dataset` artifacts, so a caller of these workflows runs `engine.yml` first.
- **Continuous integration skips the work that a change cannot affect.** `.github/scripts/changed-areas.js` decides which jobs start: `AREAS_BY_PREFIX` maps a changed path to the TypeScript jobs, a path that no prefix matches starts every TypeScript job, and `PATHS_BY_LANGUAGE_AREA` lists the paths that start each language workflow. A Markdown change starts a job only where it touches a guide directly under `docs/`, a file under `skills/`, or a package README that `MARKDOWN_THAT_THE_CHECK_JOB_COMPILES` or a `compiledMarkdown` list holds, because a job compiles the code blocks of each of those files. The path lists of the Rust, Python, and Go engine workflows leave out the TypeScript folders that `dist/index.mjs` never bundles. Add each new package or folder to both tables. Keep the `Performance` workflow unfiltered, because CodSpeed posts its required check only after a run. Keep every required check a job of `ci.yml` or of its own workflow, because GitHub names a job inside a called workflow `<caller> / <job>`, and gate a required job's steps where a matrix job would otherwise skip, because a skipped matrix never reports its required check names. Keep a separate concurrency group for each push to `main` in `ci.yml` and none inside a called workflow, because a push run tests only the files that its push changed, so a later push must never cancel it.
- **Root `pnpm test` skips the example apps.** It excludes `@delali/narsil-example-*` and covers the three packages plus the benchmarks project. Run `pnpm test:examples` when you change the browser or server-app example.
- **A generator writes `BENCHMARKS.md`, `nx release` writes each `CHANGELOG.md`, and `packages/ts/wasm/build.ts` writes `src/vector/simd-wasm-binary.ts`.** `benchmarks/writeup/generate.py` fills the regions between the `<!-- BENCH:<id> START -->` markers from the newest recorded run, including the `BENCH:headline` region in the root `README.md` and in `packages/ts/README.md`, while `benchmarks/writeup/charts.py` draws the SVG figures the page embeds into each run's `charts/` directory. Continuous integration fails when the committed page or any committed figure differs from a fresh generation. Edit the source each one reads, and draw the charts before you regenerate the page.
- **Continuous integration compiles every code block in the guides, the skill, and the package READMEs.** `.github/scripts/check-guide-examples.js` compiles each TypeScript, Python, and Go block in the guides directly under `docs/` and in the Markdown files under `skills/`, while `.github/scripts/check-readme-examples.js` compiles each README block in its package's language, inside the workflow that tests that package. Both scripts also execute each block marked `run`, so mark a README block `run` when it needs no network and no outside service, and mark a guide block `run` when the guide states its output. Mark `skip` on a block that cannot compile, such as a shell command or JSON. Give a fragment the imports and the values that the reader's code supplies in an `<!-- example setup ... -->` comment directly above its fence, where a line that holds `{example}` marks the place of the block inside the setup. When a visible line fails to compile, the page disagrees with the API, so fix that line and leave the setup to declare only what the reader supplies.
- **Wrap every line that gives a released Narsil version in `<!-- release-version <project> -->` and `<!-- /release-version -->`.** `check-release-versions.js` fails when a Markdown file outside the CHANGELOGs, `packages/spec`, and the benchmark records contains a Narsil version outside those markers, or when a marked version differs from the project manifest. Each nx version action rewrites the marked lines of its project before `nx release` makes the release commit. A Go module takes its version from its tag alone, so the check refuses a version in a Go README.
- **`scripts/openapi/generate.ts` writes `packages/ts/openapi.json` from `serverRoutes` and the types in `HttpWireTypes`.** Continuous integration fails when the committed file differs from a fresh generation, so run `pnpm nx run narsil-ts:openapi:write` after you change a route or a type that a route sends or takes, and add each new route to `src/__tests__/server/openapi/operation-cases.ts`. `test:openapi-clients` generates Python and Go clients through Docker, and the default test target skips it.
- **A benchmark run is a committed artifact.** The writeup reads the newest run directory under each suite's `results/`, so running a suite changes what the published page reports. Run one only when you're asked to.
- **A dataset artifact is pinned by digest.** Each `[[datasets]]` entry in `benchmarks/server/config/benchmark.toml` names an `artifact_sha256`, the digest of the published `artifact.json` that lists every vector shard and text file with its own digest. Rebuilding an artifact changes that digest, so publish it through the `Publish dataset artifact` workflow, paste the digest it prints into the config, and expect the `Benchmark harness tests and pinned dataset digests` job to fail until the digest in the config matches the published manifest. The local copies under `benchmarks/server/artifacts/` are git-ignored.
- **`etcd3`, `@grpc/grpc-js`, and `uWebSockets.js` are optional peer dependencies.** `distribution/coordinator/etcd/loader.ts`, `distribution/transport/grpc/loader.ts`, and `server/runtime.ts` load them by dynamic import, and each one raises a typed error naming the install command. A static import of any of them breaks every install that leaves the optional dependency out.
- **A write during rebalancing goes to the write-ahead queue.** `partitioning/write-ahead-queue.ts` throws `PARTITION_REBALANCING_BACKPRESSURE` once it holds 10,000 entries, and it replays entries in sequence-number order.
- **The write-ahead log and the replication log share one entry format.** `persistence/durability/manager.ts` builds each log record with `buildEntry` from `distribution/replication/entry-checksum.ts`, so a change to `ReplicationLogEntry` or to its checksum changes what recovery reads off disk.
- **A worker never receives live partition state.** `serializePartition` in `core/partition/serialization.ts` converts it first and maps internal ordinals back to external document IDs. Convert any new structure that holds internal ordinals the same way.
- **The dependency age gate refuses a package published less than four days ago,** and the supply-chain gate refuses an unpinned action reference, a `pull_request_target` trigger, and any URL dependency other than the pinned `uWebSockets.js`.

Read `CONTRIBUTING.md` for the house style and `ROADMAP.md` for where the project is heading. Cluster mode under `src/distribution/` is the project's active focus, so preserve its recovery and failover invariants when you change replication or bootstrap code.

## Agent skills

### Issue tracker

This repo keeps its issues as GitHub issues on `assetcorp/narsil`, and you perform every operation through the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

This repo uses five canonical triage roles, where each label string equals the role's own name. See `docs/agents/triage-labels.md`.

### Domain docs

This repo is single-context: one `CONTEXT.md` and one `docs/adr/` at the repo root cover all five packages. See `docs/agents/domain.md`.
